# DECISIONS — 설계 결정 기록 (ADR)

§67에 따라, 사소한 구현 선택은 사용자를 멈춰 세우지 않고 스스로 결정한 뒤 여기에 기록합니다.
**사용자 승인이 필요한 항목은 맨 아래 별도 섹션**에 모아두었습니다.

---

## D-001 · 픽셀 렌더링은 Canvas 2D로 시작 (PixiJS 아님)
- **날짜**: 2026-09-02
- **선택지**: PixiJS 8 (WebGL/WebGPU, MIT) vs Canvas 2D (브라우저 내장)
- **결정**: **Canvas 2D.** `OfficeRenderer` 인터페이스 뒤에 숨겨 교체 가능하게.
- **근거**:
  1. MVP 동시 표시 캐릭터 14명. WebGL 엔진이 필요한 규모가 아니다.
  2. `pixel-agents`(⭐9.2k)가 Canvas 2D만으로 같은 UX를 구현하고 있다 — 실증 사례.
  3. §9 "복잡성을 위해 기술을 추가하지 마라"
- **번복 조건**: 동시 캐릭터 60명 이상에서 60fps 미달 시 `PixiJSRenderer.ts` 추가 (파일 하나만 늘어남)

## D-002 · TradingAgents를 포크하지 않고 설계만 참고
- **결정**: Apache-2.0이라 병합해도 합법이지만 **코드는 가져오지 않는다.**
- **근거**: TradingAgents에는 우리 필수 요구사항인 **Point-in-Time(§20), Evidence Graph(§27), Research Firewall(§22)이 없다.** 껍데기를 가져오면 그 셋을 다시 뜯어 넣어야 해서 순이득이 없다. 가져오는 것은 4단 파이프라인 구조와 LangGraph 토론 패턴.
- **번복 조건**: 없음

## D-003 · 기본 지표 엔진은 pandas-ta-classic, TA-Lib은 선택적 가속
- **결정**: `pandas-ta-classic`(MIT, 순수 파이썬)을 기본. `TA-Lib`(BSD-2)은 있으면 쓰고 없으면 무시.
- **근거**: Windows에서 TA-Lib C 라이브러리 빌드가 실패하면 **전체 시스템이 멈추면 안 된다.** 조사 시점 기준 Windows wheel이 제공되지만, 의존해서는 안 되는 종류의 것이다.
- **결과**: `chart_skills`는 `talib` import 실패를 정상 경로로 처리한다.

## D-004 · 포트를 기본값에서 비켜서 할당
- **결정**: postgres **5433**, redis **6380**, api **8010**, web **3010**
- **근거**: 5432/6379/8000/3000은 antking님의 다른 프로젝트(AI SNS 콘텐츠 공장, TikTok 도구 등)가 쓸 확률이 높다. **다른 프로젝트를 종료시키는 대신 우리가 비켜간다** (§4).
- **비고**: `audit.ps1`이 실제 사용 현황을 확인하고, 충돌 시 `.env`에서 +1씩 조정

## D-005 · Docker Compose project name과 볼륨 접두사 고정
- **결정**: project `ai-stock-research-office`, 볼륨 `airo_pgdata` / `airo_redisdata`, 컨테이너 `airo-*`
- **근거**: 다른 프로젝트 리소스와 절대 섞이지 않게. `reset-local.ps1`이 이 스코프 밖을 건드릴 수 없게.

## D-006 · LiteLLM을 LLM 게이트웨이로 채택 (단, 한 겹 더 감싼다)
- **결정**: `packages/llm_gateway/interface.py`(우리 인터페이스) → `litellm_impl.py`(구현체)
- **근거**: LiteLLM(MIT, ⭐53.8k)이 §51(모델 독립성) + §52(라우팅) + §54(비용 추적)를 한 번에 해결한다. 직접 만들면 공급자별 가격표를 계속 따라다녀야 한다.
- **왜 한 겹 더 감싸는가**: §51의 정신은 "특정 LLM에 종속되지 않는다"인데, LiteLLM 자체에 종속되면 같은 문제다.

## D-007 · Job Queue는 Celery 아닌 arq
- **결정**: `arq`(MIT, Redis + asyncio)
- **근거**: Celery는 Windows 공식 지원이 중단되었다. 컨테이너 안에서 돌리면 되지만 1인 개발자의 디버깅 부담이 크다. arq는 작고 FastAPI(asyncio)와 궁합이 맞다.

## D-008 · Point-in-Time은 프롬프트가 아니라 코드로 강제
- **결정**: 에이전트는 DB에 직접 접근할 수 없다. `PITQuery(as_of)`를 통해서만 접근하며 `as_of`는 워크플로가 주입한다.
- **근거**: §20은 이 프로젝트에서 가장 중요한 요구사항이다. "미래를 보지 마세요"라고 프롬프트로 부탁하면 LLM은 반드시 언젠가 어긴다. **구조적으로 불가능하게 만든다.**

## D-009 · Bull/Bear 격리도 데이터 구조로 강제
- **결정**: LangGraph state에 `bull_channel` / `bear_channel`을 분리. DEBATE 노드 이전에는 상대 채널이 프롬프트 컨텍스트에 들어가지 않는다.
- **근거**: D-008과 같은 이유. §12를 프롬프트 지시로 처리하면 새어나간다.

## D-010 · Evidence Gate는 리포트 발행을 차단한다
- **결정**: 최종 리포트의 모든 숫자에 `evidence_id`가 없으면 **예외를 던지고 발행하지 않는다.**
- **근거**: §25 "중요 숫자는 Evidence ID 없이 Final Report에 포함하지 않는다"를 실행 가능한 형태로 옮긴 것. 경고 로그로 처리하면 아무도 안 본다.

## D-011 · MVP 프로세스 수를 최소화 (services/learning_worker 안 만듦)
- **결정**: `scheduler`가 학습 잡을 큐에 넣고 `agent_runtime`이 처리한다. 별도 학습 워커 프로세스는 만들지 않는다.
- **근거**: §10의 구조는 참고안이며, 문서에서 이유를 설명하라고 명시되어 있다. 프로세스가 늘수록 Windows에서 디버깅이 어려워진다. 부하가 실제로 생기면 그때 분리한다.

## D-012 · 뉴스 기사 전문을 DB에 저장하지 않는다
- **결정**: URL, 제목, 발행일, 원문 소스, **추출된 사실 + 짧은 인용**, content_hash만 저장. 전문 보관 안 함.
- **근거**: 저작권. 그리고 §22의 정신 — 우리가 원하는 건 기사가 아니라 **검증된 사실**이다.

## D-013 · 근사 중복 탐지를 반드시 넣는다 (MinHash/SimHash)
- **결정**: `datasketch`(MIT) 또는 자체 SimHash
- **근거**: §23을 content_hash만으로 구현하는 것은 불가능하다. 신디케이션 기사는 사이트마다 문단이 조금씩 다르다. 이게 없으면 "50개 사이트가 확인함" 버그가 그대로 남는다.

## D-014 · Redis 대신 Valkey로 교체 가능하게 설계
- **결정**: 코드는 Redis 프로토콜만 사용. 특정 벤더 기능 안 씀.
- **근거**: Redis 라이선스가 최근 몇 년간 변경되어 왔고, 사용 시점 상태를 확인해야 한다(Phase 5). Valkey(BSD-3-Clause)가 프로토콜 호환 대체재로 존재하므로 최악의 경우에도 막히지 않는다.

## D-015 · UI는 Mock 데이터를 절대 실제처럼 표시하지 않는다
- **결정**: 모든 이벤트/데이터에 `is_mock` 플래그. true면 화면에 `MOCK DATA` 배지.
- **근거**: §44, §63, §66. 이건 타협 대상이 아니다.

## D-016 · 문서와 코드 주석은 한국어, 코드 식별자는 영어
- **결정**: 변수/함수/테이블명은 영어, 문서·주석·UI 텍스트는 한국어.
- **근거**: antking님이 한국어로 소통하시고, 코드는 오픈소스 생태계와 섞여야 한다.

## D-017 · 서버를 두 벌로 만든다 (FastAPI + 표준 라이브러리)
- **날짜**: 2026-09-02
- **결정**: `services/api/main.py`(FastAPI)와 `services/api/standalone.py`(표준 라이브러리)를 둘 다 제공. 로직은 `services/api/routes.py` 한 곳에서 공유.
- **근거**:
  1. "아무것도 설치되지 않아도 일단 화면이 떠야 한다"가 초보 사용자에게 결정적입니다. pip 이 막히거나 Node 가 없어도 파이썬만 있으면 픽셀 사무실이 뜹니다.
  2. 개발 중인 클라우드 환경에서 PyPI 접근이 막혀 FastAPI 를 설치할 수 없었습니다. 그 상태에서도 전체 시스템을 실제로 돌려보고 테스트해야 했습니다.
- **분기 방지**: 두 서버가 같은 `routes.py` 함수를 호출하므로 응답이 달라질 수 없습니다. `tests/test_api_contract.py` 가 두 서버의 경로 집합이 같은지 AST 로 검사합니다.
- **비용**: WebSocket 을 직접 구현해야 했습니다(핸드셰이크 + 프레임 인코딩/디코딩, 약 90줄). RFC 6455 예제값으로 검증했습니다.

## D-018 · 핵심 로직에 외부 패키지를 쓰지 않는다
- **결정**: `chart_skills`, `learning_engine`, `source_validation`, `evaluation`, `backtest_engine`, `pattern_miner`, `pit_store`, `agent_registry` 전부 표준 라이브러리만 사용.
- **근거**: 위 D-017 과 같은 이유 + 테스트 가능성. pydantic 을 agent_registry 에서 걷어내고 dataclass 로 바꿨습니다.
- **PyYAML 대응**: `packages/shared/miniyaml.py` 를 만들고, PyYAML 이 있으면 그것을 씁니다. **설정 파일 13개 전부에서 두 파서의 결과가 완전히 일치**하는 것을 테스트로 검증했습니다.
- **번복 조건**: Phase 16 에서 pandas-ta-classic 을 도입하면 chart_skills 는 외부 의존성을 갖게 됩니다. 다만 현재 구현은 "정답 대조용 기준값"으로 남깁니다.

## D-019 · Redis 대신 Valkey 를 기본으로
- **결정**: `docker-compose.yml` 에서 `valkey/valkey:8-alpine` 사용.
- **근거**: Redis 라이선스가 최근 몇 년간 변경되어 왔습니다. Valkey 는 프로토콜 호환 포크이고 **BSD-3-Clause** 로 명확합니다. 나중에 라이선스 문제로 갈아엎느니 처음부터 안전한 쪽을 씁니다.
- **비용**: 없음. 코드는 Redis 프로토콜만 쓰므로 언제든 되돌릴 수 있습니다.

## D-020 · 학습 시간을 "가속 시뮬레이션"이라고 명시한다
- **결정**: `/api/system/health` 에 `time_scale: "ACCELERATED_SIMULATION"` 을 항상 포함하고 Learning 화면에도 표시.
- **근거**: 1틱마다 학습 단계가 진행되므로 화면의 "250분 학습" 은 실제 250분이 아닙니다. 이걸 숨기면 사용자가 숫자를 오해합니다.
- **원칙**: 실제 데이터와 데모 데이터를 명확히 구분한다 (§66).

## D-021 · 예측 저장에 상한을 둔다
- **결정**: `PredictionJournal.max_predictions = 2000`, 초과 시 오래된 것부터 제거.
- **근거**: 차트 학습 예측을 전부 저널에 기록하기로 하면서, 오래 돌리면 메모리가 무한히 늘어납니다. Phase 5 에서 DB 로 옮기면 이 상한은 사라집니다.

## D-023 · 캘리브레이션은 구간별(ECE)로 계산한다

## D-029 · 외부 수집 도구는 붙이되, 절대 신뢰하지 않는다 (Agent Reach)
- **날짜**: 2026-09-03
- **상황**: 사용자가 Agent Reach 설치를 요청. 웹·RSS·YouTube·Reddit·Twitter 등을 CLI 하나로 감싸주는 도구입니다.
- **결정**: **어댑터 계층으로만 붙입니다.** 코드 병합 없음, `subprocess` 호출만.
  - 자동 설치 금지 (자격증명이 걸린 행위 = 사용자 승인 사항)
  - 쿠키 필요 채널(Twitter/Instagram/LinkedIn/샤오홍슈) **기본 차단**
  - 설치 스크립트에서 `--system` 금지
  - 수집 결과는 **전부 Research Firewall 통과 + 우리 규칙으로 등급 재판정**
- **근거**:
  1. 편의를 얻는 대신 **판정 권한을 넘기면 안 됩니다.** 도구가 레딧에서 가져와도 그건 Tier E 입니다.
  2. 쿠키 인증은 대부분 플랫폼 약관 위반이고 계정 정지 위험이 있습니다. 도구 문서 스스로 "부계정을 쓰라"고 합니다.
  3. 설치 소스가 `main.zip` 이라 **버전이 고정되지 않습니다.** 그 코드가 세션 쿠키를 다룹니다 — 공급망 위험.

## D-030 · 모든 `.ps1` 은 UTF-8 **BOM + CRLF** 로 저장한다

**문제.** antking님 PC 에서 `setup.ps1` 이 ParserError 로 실행되지 않았습니다.
제 개발 환경(PowerShell 7 / Linux)에서는 21개 스크립트가 전부 구문검사를 통과했는데도요.

**원인.** Windows 10/11 의 기본 셸은 **Windows PowerShell 5.1** 입니다.
5.1 은 BOM 이 없는 `.ps1` 을 UTF-8 이 아니라 **시스템 ANSI 코드페이지**로 읽습니다.
한국어 Windows 에서는 CP949 입니다.

UTF-8 한글은 3바이트, CP949 는 2바이트라 정렬이 어긋납니다.
그러다 어떤 한글의 마지막 바이트가 CP949 **선행 바이트(0x81–0xFD)** 로 해석되면,
디코더가 **바로 다음 바이트까지 한 글자로 삼킵니다.** 그 다음 바이트가 줄바꿈(0x0A)이면
**줄이 통째로 사라집니다.**

실측: `setup.ps1` 은 318줄인데 PowerShell 5.1 은 **314줄**로 봤습니다.
줄 4개가 사라지면서 코드가 주석 안으로 밀려 들어갔고, 파서가 깨졌습니다.
사용자 오류 메시지의 줄번호(84, 92)가 시뮬레이션 결과와 **정확히 일치**해 확인했습니다.

**결정.**

1. 모든 `.ps1` 을 **UTF-8 BOM** 으로 저장한다 → 5.1 도 UTF-8 로 읽는다 (1차 방어선)
2. 줄바꿈을 **CRLF** 로 고정한다 → 선행 바이트가 삼켜도 CR(0x0D)만 먹히고 LF 는 살아남는다 (2차 방어선)
3. `.bat` 은 **ASCII 전용** 으로 둔다 → cmd.exe 는 OEM 코드페이지로 읽으므로 한글을 넣지 않는다
4. 콘솔 출력에서 CP949 로 표현 못 하는 문자(`—` U+2014)를 쓰지 않는다 → `-` 로 대체

**테스트로 고정** (`TestPowerShellFileEncoding`):

- `test_every_ps1_has_utf8_bom`
- `test_every_ps1_is_valid_utf8`
- `test_ps1_files_use_crlf`
- `test_parses_the_same_after_ansi_misread` — CP949 디코더를 흉내 내어
  **줄바꿈이 하나도 사라지지 않는지** 직접 계산합니다

**교훈.** "제 환경에서 통과"는 "사용자 환경에서 동작"이 아닙니다.
PowerShell 7 로만 검증한 것이 실수였습니다. 개발 환경과 실행 환경이 다르면,
**차이 그 자체를 테스트로 만들어야** 합니다.

## D-036 · 패턴은 통계 관문 4개를 전부 통과해야 STRONG 이다

**문제.** 문서에 이렇게 적혀 있었습니다.

> Pattern Miner 다중검정 미보정 — 153개 테스트 시 5%는 우연히 유의.
> **가장 큰 통계적 약점**

후보 153개를 검정하면 우위가 전혀 없어도 약 8개가 우연히 유의합니다.
그 상태로 "STRONG 8개 발견"은 아무 의미가 없습니다.

**결정.** 관문 3개를 추가합니다.

1. **Walk-forward 일관성 ≥ 60%** — 한 번의 분할 운을 N회 관측으로 바꿉니다
2. **겹치는 표본 보정** — 5일 수익률을 매일 재면 표본 100건의 실질 정보량은
   약 20건입니다. 보정하지 않으면 p-value 가 실제보다 훨씬 작게 나옵니다
3. **Benjamini-Hochberg FDR** — 동시 검정 수를 반영합니다.
   Bonferroni 도 함께 계산해 보여줍니다

**실측 효과** (합성 6종목 700봉): STRONG 이 8개 → **5개**로 줄었고,
walk-forward 에서 8개, 다중검정 보정에서 **43개**가 추가로 기각되었습니다.
그 43개는 보정이 없었다면 STRONG 으로 보고되었을 후보들입니다.

보고서에 보정 전후를 **나란히** 적습니다. "보정이 없었다면 우연만으로도
약 N개가 유의하게 나왔을 것" 이라는 문장이 항상 붙습니다.

**여전히 사실인 것.** 보정은 잘못된 발견을 줄이는 도구이지 옳은 발견을
만드는 도구가 아닙니다. 이 관문들의 목적은 "많이 찾기"가 아니라
**"자신 있게 버리기"** 입니다.

## D-037 · SEC 는 연락처 이메일이 없으면 요청 자체를 만들지 않는다

`filed` 필드가 없는 XBRL 사실은 **버립니다** — 언제 알 수 있었는지 모르는
값은 쓸 수 없습니다.

## D-039 · 공공데이터포털 serviceKey 는 인코딩을 자동 판별한다

**이 API 최대의 함정입니다.**

data.go.kr 은 키를 'Encoding' / 'Decoding' 두 형태로 줍니다.
Decoding 키에는 `+` 가 들어 있는데, 그것을 URL 에 그대로 붙이면
서버의 URL 디코더가 **`+` 를 공백으로** 바꿉니다.

    보낸 키    abc+def
    서버가 읽음 abc def          ← 키가 달라졌습니다
    결과       SERVICE_KEY_IS_NOT_REGISTERED_ERROR

키는 멀쩡한데 "등록되지 않은 키" 라고 나옵니다. 원인을 찾기 매우 어렵고,
초보자라면 여기서 포기하게 됩니다.

**결정.** 어느 형태를 주셔도 되도록 자동 판별합니다.

    Decoding 키(`+` `/` `=` 포함)  → 인코딩해서 전송
    Encoding 키(`%2B` 포함)        → 그대로 전송
                                     (또 인코딩하면 `%` 가 `%25` 가 되어 다시 깨짐)

양방향 모두 테스트로 고정했습니다. 로컬 스텁 서버로 "잘못 보내면 실제로
실패하고, 바르게 보내면 성공한다" 는 것까지 실측했습니다.

**부수 결정.** 이 API 는 JSON 을 요청해도 오류일 때는 XML 을 돌려줍니다.
그것을 처리하지 않으면 "JSON 파싱 실패" 라는 쓸모없는 메시지만 남습니다.
XML 안의 `returnAuthMsg` 를 뽑아 **실제 사유와 조치 방법**을 한국어로 안내합니다.

## D-040 · DART 재무제표는 접수일자 없이 PIT 레코드를 만들지 않는다

SEC EDGAR 의 `filing_date` 규칙(D-037)과 같은 문제가 DART 에도 있습니다.

    결산기말      2024-12-31   그 숫자가 '언제의 실적인가'
    rcept_dt      2025-03-11   그 숫자를 '언제 알 수 있었나'

결산기말을 기준으로 쓰면 **12월 31일에 이미 연간 실적을 아는 것**이 됩니다.
두 달 반의 미래를 보는 셈입니다.

**여기에 DART 만의 함정이 하나 더 있습니다.**
`fnlttSinglAcnt.json`(단일회사 주요계정) 은 숫자를 주지만
**언제 공시됐는지는 돌려주지 않습니다.** 그 숫자만 보고 저장하면
"언제 알 수 있었는지 모르는 값" 이 됩니다.

**결정.** `rcept_dt` 없이는 PIT 레코드를 **만들지 않고 예외를 던집니다.**
숫자를 화면에서 보는 것은 허용하되, 그때는 경고를 함께 표시합니다.

    "★ 접수일자를 주지 않아 PIT 레코드를 만들지 않았습니다.
      이 숫자들이 언제 공개됐는지 알 수 없으므로 백테스트에 쓰면
      미래 정보가 섞입니다."

편의를 위해 결산기말로 대충 채우는 선택지도 있었지만, 그건 조용히 틀리는
쪽입니다. **거부하고 이유를 말하는 편이 낫습니다.**
